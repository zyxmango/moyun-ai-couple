# 长期记忆生产架构

本文描述当前实现。仓库中的早期设计文档保留了项目演进过程，涉及 TF-IDF、固定最近窗口或人工确认的段落不再代表现状。

## 数据流

1. 聊天、日记、相册和纪念日写入业务表后，只提交一个幂等同步任务，请求无需等待模型处理。
2. 独立 Memory Worker 按情侣领取任务，通过同步游标持续补齐未处理数据。失败任务会退避重试，租约到期后可由其他 Worker 接管。
3. 原始聊天完整保留；记忆表只保存事件、偏好和事实。模型按对话窗口抽取，并通过稳定来源标识、事件状态和相似事件合并避免碎片化与重复。
4. Embedding 持久化。Compose 环境使用 PostgreSQL 与 pgvector HNSW；本地开发可继续使用 SQLite 的持久化向量和 LSH 候选索引。
5. 查询先执行情侣、所有者和可见性过滤，再做语义候选召回与混合排序，最后只把 Top-K 证据交给回答模型。
6. 回答必须由检索证据支持；无依据时返回不知道，引用可追溯到记忆及原始来源。

## 运行方式

Compose 会同时启动 PostgreSQL、API、Memory Worker 和前端：

```powershell
Copy-Item backend/.env.example backend/.env
docker compose up --build
```

直接在 Windows 启动时，`start-app.bat` 会分别启动 API、前端和 Memory Worker。默认不在 API 进程内运行 Worker，避免多实例部署时重复扫描。

## 监控

管理员统计页显示同步积压、失败任务、未生成向量的记忆、近 24 小时失败率、同步耗时、模型调用量、Token 和估算成本。接口只返回汇总指标，不返回聊天或记忆正文。

重点告警条件：

- 最大消息积压持续上升；
- 失败任务或未向量化记忆不归零；
- 24 小时失败率异常；
- P95 同步耗时、调用量或估算成本突增。

## 评测

`eval_memory_e2e.py --smoke` 使用缩减的合成数据验证抽取完整性、状态与时间、检索召回、回答依据和拒绝编造。

`eval_memory_anonymized.py --prepare-couple <id>` 只在本机生成匿名标注模板。人工把可评测样本标为 `reviewed=true` 后，再用 `--input` 执行。报告仅保留聚合结果和布尔判定，不包含原始聊天、问题或答案。`backend/data/private_evals/` 已从版本控制排除。

## 部署边界

- SQLite 用于单机开发与演示；长期运行和多实例部署使用 PostgreSQL/pgvector。
- `.env`、真实聊天、匿名标注工作文件和本地数据库不得提交到仓库。
- 修改生产数据库结构时应使用正式迁移流程；不要依赖应用启动时的本地轻量迁移。
